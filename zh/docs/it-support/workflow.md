# IT 支持工作流程

## 1. 明确问题

询问：原本想完成什么？实际发生了什么？准确报错是什么？上次正常是什么时候？还有谁受到影响？最近变更了什么？

具体描述影响：单个用户登录、某个服务、一个站点，还是整条业务流程。使用组织的事件优先级规则；紧急程度与影响范围应分别判断。

## 2. 确定范围

在获得授权的前提下，对比失败与正常场景：不同用户、设备、网络或应用访问路径。一次有针对性的对比，往往比十个无关命令更能缩小故障范围。

| 差异 | 排查方向 |
| --- | --- |
| 同一用户在多台设备上都失败 | 身份、权限或用户专属配置 |
| 多个用户在同一设备上失败 | 设备、本地配置或终端网络连接 |
| 仅一个网段失败 | 路由、DNS、代理、防火墙或运营商路径 |
| 所有客户端访问同一服务都失败 | 服务健康、依赖、容量或近期部署 |

这些只是线索，不是诊断结论。先验证，再变更。

## 3. 收集少量关键证据

包含准确时间与时区、失败操作、简短错误摘录及相关系统和版本信息。仅收集事件时间窗口所需的日志。分享前去除令牌、个人信息和查询中的敏感字面值。

Linux 问题从[快速检查](../quick-check.md)开始。数据库问题要区分客户端传输、服务器健康、身份验证、权限及查询性能。

## 4. 提出一个可验证的假设

例如：“应用无法连接，是因为目标服务没有监听配置的地址。”检查服务器套接字与应用目标，再对比结果。仅凭超时不能认定是防火墙问题。

## 5. 变更、验证与记录

明确负责人及所需变更授权。执行前记录预期结果和回滚方案。重启或清理前保留相关证据。

同时验证技术指标和受影响用户的操作。记录什么确实有效、哪些仍不确定、谁负责跟进。升级处理时带上证据和具体问题，而不是只说“还是坏的”。
