# MySQL 故障排查

先记录准确报错、目标主机与端口、连接方式、服务器版本、事件时间和应用影响。变更前查看[连接与 SQL 速查](commands.md)。

| 症状 | 首先区分 | 下一项检查 |
| --- | --- | --- |
| `ERROR 2002` 本地连接失败 | 套接字路径、服务状态或本地传输 | 对比配置的套接字与明确使用 TCP 的测试 |
| `ERROR 2003` 无法连接服务器 | 目标、监听及传输路径 | 检查 DNS、路由、监听地址与端口 |
| `ERROR 1045` 访问被拒 | 账户匹配与身份验证 | 核对用户、来源、认证方式、凭据来源和 TLS 要求 |
| `ERROR 1044` 数据库访问被拒 | 已连接账户缺少所需权限 | 对比匹配账户与获批授权 |
| `ERROR 1040` 连接过多 | 连接容量耗尽 | 对比当前会话、运行工作、应用池与服务器限制 |
| `ERROR 1205` 锁等待超时 | 阻塞或其他锁等待 | 确认等待者、阻塞者与事务时长 |
| `ERROR 1213` 死锁 | 事务操作顺序冲突 | 记录相关死锁证据和应用重试行为 |
| 无连接错误但响应缓慢 | 查询、锁、资源或网络延迟 | 关联应用耗时、服务器负载、执行计划与主机指标 |

错误码能缩小范围，不能独立给出完整根因。

## 无法连接

确认应用实际使用的目标、端口与传输方式。本地 Unix 套接字和 TCP 行为可能不同。自建 Linux 服务应确认单元名是 `mysql`、`mysqld` 还是其他名称。托管服务应使用其状态、指标与网络控制，不要假设可以登录 Shell。

按[网络排查](../linux/networking.md)逐层验证。传输正常但认证失败时，与授权管理员核对匹配账户及配置。不要通过开放所有来源或关闭 TLS 校验解决账户匹配问题。

## 连接过多（Too many connections）

对比 `Threads_connected`、`Threads_running`、`Max_used_connections` 与 `max_connections`，查看会话时长和应用连接池配置。排查连接泄漏、异常部署或重试激增，以及长事务阻塞的会话。

提高服务器连接上限可能增加内存压力并掩盖连接池问题。变更容量或结束会话前，先记录证据并让应用或数据库负责人参与。

## 查询缓慢或被阻塞

1. 确定具体受影响请求与时间窗口。
2. 检查活动会话和长时间未结束的 InnoDB 事务。
3. 使用两个 `sys` 视图区分行锁等待和元数据锁等待。
4. 比较一段时间内的语句摘要变化，不要把历史累计最高的语句直接认定为本次原因。
5. 对已知查询和代表性参数查看普通 `EXPLAIN`。小表选择全表扫描可能是合理的。
6. 对比 CPU、可用内存、I/O、存储容量及应用和网络耗时。

权限足够时，`SHOW ENGINE INNODB STATUS\G` 可展示最近一次检测到的死锁及其他引擎信息。它是快照，可能包含敏感语句，也可能已不再反映当前事件。

若某个事务造成阻塞，先明确其业务操作与回滚后果。不要未经判断就把自动生成的 `KILL` 建议复制到生产环境。

## 数据恢复请求

明确恢复时间点和可接受停机时间。修改真实数据库前，先确认备份覆盖范围，并在隔离目标中验证恢复。参考[备份与恢复](backup-and-restore.md)；涉及在线恢复或按时间点恢复时，应让服务负责人参与。

使用[简短事件记录](../../templates/incident.md)升级处理，说明已知事实、仍不确定的事项及希望执行的下一步。
